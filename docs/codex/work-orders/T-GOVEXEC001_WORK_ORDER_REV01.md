## 6. Approved governance delta

Implement the following approved changes.

### 6.1 Repository-owned work-order doctrine

- Detailed implementation reasoning, exact files, checks, stop conditions, and closeout requirements belong in repository-owned work orders.
- External dispatch prompts should be minimal pointers to the active repository work order.
- Chat discussion and approval are not durable implementation authority until promoted.
- Do not create a second work-order owner if `CODEX_EXECUTION_STANDARD_REV01.md` can own the rule.

### 6.2 Targeted-read and token-efficiency doctrine

- Preserve targeted reads as the default.
- Require every work order to name the minimum authority and owner document set.
- Require closeout to identify essential reads, unnecessary reads, broad/full-read justifications, retries, context pressure, and a shorter next-run prompt pattern.
- Do not create a durable token log.

### 6.3 Architecture Steward Contract

Formalize the ChatGPT architecture-steward role as a governed role, independent of a specific model version.

The steward must:

- protect repository-first governance;
- preserve business-capability ownership;
- reconcile before creating or duplicating;
- perform governance impact assessment before governance implementation;
- prefer extending an existing owner over creating a parallel owner;
- keep implementation bounded;
- protect additive/destructive discipline;
- surface conflicts and stop rather than silently bypassing them;
- use targeted reads and context-efficient dispatch;
- review Codex closeout and RSI findings;
- route approved improvement candidates into durable authority;
- remain technology-agnostic and replace adapters rather than operating doctrine.

The steward must not merge, invent strategy, activate protected work, or substitute chat memory for repository authority.

### 6.4 MTR active-dispatch-board doctrine

- Define the Master Task Register as the live dispatch board.
- It should retain tasks that are active, ready, planned, blocked, waiting, deferred, review, merged, deployed, or main-synced pending scheduled archival.
- Do not use this task to purge historical records unless an exact archive migration is explicitly safe and bounded from current evidence.
- Completed-history cleanup occurs on a weekly stewardship cadence, not during every task closeout.
- Preserve proof-of-work links and identifiers during archival.

### 6.5 Completed Task Register doctrine

Create a canonical Completed Task Register only if no current canonical completed-history owner already exists.

The CTR must:

- preserve minimal proof-of-work fields;
- support later KAOS Mission History / Operational History viewing;
- record task ID, task name, business capability, category/workstream, completion date, PR, merge evidence, deployment applicability/status, main-sync status, governing context, and concise result;
- avoid duplicating full PR or implementation history already retained in GitHub;
- be updated through weekly stewardship after merge, relevant deployment verification, and main synchronization are complete;
- remain historical evidence and never authorize implementation.

If an equivalent owner exists, amend it rather than creating a duplicate.

### 6.6 Standing Campaign Authorization doctrine

- Define standing campaign authorization as category-level permission to create and sequence bounded tasks inside an approved campaign.
- It does not itself authorize source edits, website changes, runtime changes, protected-system changes, or multi-task bundling.
- Every implementation still requires one bounded task/work order.
- Website/runtime/protected systems remain individually authorized.
- Do not create or activate a new campaign in this task; govern the authorization mechanism only.

### 6.7 Weekly Repository Stewardship doctrine

Define a weekly governance-maintenance cadence covering:

- archive eligible completed tasks from MTR to CTR;
- preserve PR, merge, deployment, and sync evidence;
- compact the active register without deleting lineage;
- detect stale references, duplicate owners, broken links, and unresolved status drift;
- review RSI promotion candidates;
- produce a concise repository-health result;
- make no product, runtime, or implementation changes unless separately authorized.

### 6.8 Dispatcher doctrine

Preserve and clarify:

- Operator: business owner and final approver.
- ChatGPT: architecture steward, governance impact assessor, dispatcher, and closeout reviewer.
- Repository: durable authority and work-order source.
- Codex: bounded implementation technician.
- GitHub: branch, diff, PR, review, and implementation-evidence surface.
- Cloudflare: deployment/production-evidence surface when relevant.

Capability access does not create authority.

- define a minimum acceptable outcome where applicable;
- define a desired realistic outcome as a satisfaction threshold, not an exact maximum;
- allow favorable variance above that threshold when all governing risk, ethics, quality, customer, architectural, and legal constraints remain satisfied;
- do not reward additional performance obtained by violating constraints;
- do not force action when evidence does not justify action.

Do not embed stock-trading examples or create a financial-trading standard.
